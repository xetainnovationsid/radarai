# BUG-17: DICOM Part 10 Preamble Heuristic Collision with Active Content Magic Byte Detection

**Severity:** P3 (Low)  
**Component:** `apps/api/src/radar_api/dicom_upload.py` & `apps/web/lib/api-client.ts`  
**Found in:** Comprehensive Codebase Bug Audit  
**Status:** Documented / Fix Available  
**Type:** Security Heuristic False Positive / File Rejection  
**Notice:** Research prototype only — **NOT FOR CLINICAL USE**.

---

## 1. Description

In both the frontend validator ([`apps/web/lib/api-client.ts`](../../apps/web/lib/api-client.ts)) and backend upload staging ([`apps/api/src/radar_api/dicom_upload.py`](../../apps/api/src/radar_api/dicom_upload.py)), incoming DICOM uploads are scanned for executable and polyglot magic byte prefixes:

```python
# Lines 29-39 in dicom_upload.py:
FORBIDDEN_MAGIC_PREFIXES = (
    b"MZ",
    b"\x7fELF",
    b"#!",
    b"<?php",
    b"<script",
    b"<!doctype html",
    b"<html",
    b"%PDF-",
    b"PK\x03\x04",
)

# Line 108 in stage_upload():
if any(chunk.startswith(prefix) for prefix in FORBIDDEN_MAGIC_PREFIXES) ...:
    raise ValueError("Upload contains forbidden executable or active content")
```

### Root Cause
1. According to the **DICOM Standard (PS 3.10, Section 7.1: DICOM File Meta Information)**:
   > *"A 128 byte Preamble occurs at the beginning of the File Meta Information. [...] A DICOM application may use this Preamble for arbitrary purposes, or may leave it uninitialized (i.e., contain whatever is in that block of memory). No specific values or structure are defined."*
2. The authoritative DICOM Part 10 header consists strictly of the ASCII magic bytes `"DICM"` at byte offset **128–131**.
3. Many hospital workstations, CT scanner reconstruction boxes, and older PACS software do not zero out the 128-byte preamble memory buffer prior to file export.
4. If an uninitialized preamble happens to begin with bytes matching any of the prefixes (for instance, `#!` (`0x23 0x21`), `MZ` (`0x4D 0x5A`), or `PK\x03\x04` (`0x50 0x4B 0x03 0x04`) left over from previous process memory reuse):
   - The client validator rejects the file as `"terdeteksi sebagai file eksekusi/dokumen aktif yang dilarang"`.
   - The backend staging rejects the file with `HTTP 422` (`"Upload contains forbidden executable or active content"`).
5. Even though the file is a 100% valid DICOM Part 10 CT image with `"DICM"` at byte 128 and valid pixel data, the naive offset-0 prefix check erroneously rejects it.

---

## 2. Reproduction Steps

1. Create a synthetic test file with `"PK\x03\x04"` at byte 0, zero padding up to byte 127, `"DICM"` at byte 128, and a valid DICOM Part 10 dataset.
2. Attempt to upload the file via the RADAR AI upload panel or `POST /v1/studies/{id}/dicom`.
3. Observe: The upload fails immediately with `HTTP 422: Upload contains forbidden executable or active content`.

---

## 3. Impact Analysis

- **False Positive Rejections on Legacy CT Hardware**: PACS archives generated by older scanner reconstruction consoles with dirty preamble memory are blocked from upload.
- **Support Confusion**: The researcher is misled into believing their DICOM files are malicious scripts or corrupt archives.

---

## 4. Recommended Remediation

Inspect byte offset 128–131 first. If `"DICM"` is present at offset 128, only evaluate polyglot executable signatures that would be parsed by an OS loader as an executable or script, or check whether the executable header extends past offset 128:

```python
# In dicom_upload.py:
def _has_forbidden_active_content(chunk: bytes) -> bool:
    # If the file has the genuine DICOM Part 10 header at offset 128:
    if len(chunk) >= 132 and chunk[128:132] == b"DICM":
        # Disallow HTML/PHP/SVG script tags that could be exploited via browser polyglots
        head_text = chunk[:128].lower()
        if any(tag in head_text for tag in (b"<script", b"<?php", b"<html", b"<!doctype html")):
            return True
        return False

    # Otherwise, apply strict offset-0 magic prefix checks
    return any(chunk.startswith(prefix) for prefix in FORBIDDEN_MAGIC_PREFIXES)
```
